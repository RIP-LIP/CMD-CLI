# 进程与资源：谁在跑、占了多少、怎么停

> 读完你能在三十秒内回答三个问题：哪个进程在吃资源、它占的是内存还是磁盘、怎么让它干净地退出。约 25 分钟。

<ModuleMeta module-id="05-process" />

## 前置条件

**确认你手里有 ps、top、free、df 这四个。** 精简安装的容器里经常缺 `lsof`、`htop`：

```bash
command -v ps top free df
```

你应该看到四行路径。少哪个先记下来，缺的那部分本章会用替代命令说明。

确认你能看到全系统的进程（`ps` 在容器里默认只看得到当前 PID 命名空间）：

```bash
ps -p $$
```

你应该看到包含你当前 shell 那一行，`PID` 就是 `$$` 的值。**记住这个数字，本章后面用它做实验。**

## 1. 先找到进程，再谈别的

| 命令 | 是否改动数据 | 给你什么 |
| --- | --- | --- |
| `ps aux` | 只读 | 所有进程的 `USER / PID / %CPU / %MEM / VSZ / RSS / TTY / STAT / COMMAND` |
| `ps -ef` | 只读 | 同上，换成 `UID / PID / PPID / C / STIME / TTY / TIME / CMD` 视角 |
| `ps -p <PID>` | 只读 | 只看一个进程 |
| `pgrep -f '关键词'` | 只读 | 按完整命令行找 PID，**最常用的一条** |
| `top -p <PID>` | 只读 | 锁定单个进程的实时视图 |
| `ps --sort=-%mem | head` | 只读 | 按内存从大到小排 |
| `kill <PID>` | ⚠️ 改动运行状态 | 发信号，见第 3 节 |

**判断句：先用 `pgrep -f` 拿到 PID，再用 `ps -p` 确认那一条。** `ps aux | grep foo` 的输出里永远有一行是 `grep` 自己或者这条管道命令本身。

```bash
pgrep -af 'nginx'
```

`-a` 让它连命令行一起打印出来。**你应该看到 `1234 nginx: master process ...` 这样的行**，一眼能看出主进程和 worker 的区别。

### STAT 那一列才是重点

`ps aux` 的 `STAT` 列是几个字母的组合，**最需要认的是前两个**：

| 字母组合 | 含义 | 你该怎么处理 |
| --- | --- | --- |
| `R` | 正在运行或就绪 | 正常 |
| `S` | 可中断睡眠（等事件） | 正常，大部分进程平时都是这个 |
| `D` | **不可中断睡眠**（通常在等 I/O） | 机器卡顿时重点看这里；`kill -9` 也杀不掉 |
| `Z` | 僵尸：已退出，父进程没回收 | 只能找父进程，不能杀它 |
| `T` | 已用 `Ctrl+Z` 挂起 | `fg` 恢复，或 `kill` 掉 |
| `Ss` / `R+` | 首个字母是主状态，`s` 会话首进程，`+` 前台 | 不影响判断 |

**判断句：`STAT` 里有 `D` 说明瓶颈在磁盘 I/O 而不是 CPU；有 `Z` 说明有个进程没善后。** 这两种情况下 `top` 里 CPU 可能是空闲的。

### 命令名被截断到 15 个字符

```bash
cat /proc/1234/comm
tr '\0' ' ' < /proc/1234/cmdline
```

**第一个只给 15 个字符（内核里 `comm` 缓冲区就那么大），第二个给完整命令行。** 所以 `ps` 里 `my-very-long-backgr` 这种断行不是显示问题，PID 匹配不上也是因为它。**永远用 `pgrep -f` 而不是按名字匹配。**

## 2. 分清内存和磁盘

`free`、`df` 看的不是一回事。**判断句：内存不够的机器会 OOM 杀进程，磁盘满的机器上所有程序一起变慢 —— 症状不同，先分清。**

### 内存：看 available，不看 free

```bash
free -h
```

| 列 | 含义 | 能不能当依据 |
| --- | --- | --- |
| `free` | 完全没被占用的内存 | ❌ 几乎永远是「很少」，正常现象 |
| `buff/cache` | 缓冲 + 页面缓存，**需要时会立刻被回收** | ❌ 不是「被浪费了」 |
| `available` | 不做交换就能给新进程的最大额度 | ✅ **只看这一列** |
| `Swap` | 交换分区使用量 | ✅ 持续增长说明物理内存不够了 |

**判断句：`available` 接近 0 才是内存紧张，`free` 接近 0 什么都不能说明。**

### 磁盘：df 看占用，du 看谁吃的

```bash
df -h /              # 分区级别的占用，含所有挂载点
df -h --output=source,fstype,size,used,avail,pcent,target
du -x --max-depth=1 /var | sort -h
```

| 命令 | 是否改动数据 | 作用 |
| --- | --- | --- |
| `df -h` | 只读 | 各文件系统用了多少 |
| `df -i` | 只读 | **inode 数量用了多少**，见下 |
| `du -sh 目录` | 只读 | 目录实际内容占多少 |
| `du -x` | 只读 | 不跨文件系统，避免把别的挂载点算进来 |

**判断句：`df` 和 `du` 数字对不上，不要怀疑某个命令错了 —— 差额是被删除但仍被进程打开的文件。** 排法见第 4 节。

### inode 满是一个独立故障

`df -h` 显示空间还剩 40%，`touch` 却报 `No space left on device` —— 唯一可能是 inode 用光了：

```bash
df -i
```

**判断句：磁盘故障按「容量 → inode」两步查，顺序反了会白忙。** inode 满的典型来源是海量小文件（缓存目录、邮件队列、`/var/lib` 里的碎片）。

## 3. 让进程停下来

| 命令 | 是否改动数据 | 机制 |
| --- | --- | --- |
| `kill <PID>` | ⚠️ 发信号 | 默认 `SIGTERM`(15)，等于「请自行退出」 |
| `kill -TERM <PID>` | ⚠️ | 同上，写全更清楚 |
| `kill -HUP <PID>` | ⚠️ | 多数程序用来重载配置，但也有程序直接退出 |
| `kill -9 <PID>` | ⚠️⚠️ 不可撤销 | `SIGKILL`，进程**没有机会清理** |
| `kill %1` | ⚠️ | 结束当前 shell 的第 1 个后台任务 |
| `pkill -f 'pattern'` | ⚠️ | 按完整命令行批量结束，先 `pgrep -af` 确认 |

**判断句：先 `kill`（默认 TERM），等几秒还在，再 `-9`。** 这个顺序不是风格问题：

- `SIGTERM` 给程序机会关文件、提交事务、断开数据库连接。正常退出后立刻 `ps` 就看不到它了
- `SIGKILL` 是内核直接回收进程，**程序里的清理代码一行都不会跑**。写了一半的日志文件、没提交的数据库事务、遗留的临时文件和锁文件都会留下

```bash
kill 1234
sleep 3
ps -p 1234 || echo "已经退出"
```

**你应该看到 `已经退出`。** 如果还在，说明它没处理 TERM，再 `kill -9 1234`。

::: warning

`kill -9` 杀不掉的情况有两种，原因完全不同
- **`Z`（僵尸）**：进程其实已经死了，PID 还挂着等父进程回收。`kill -9` 无效。查父进程：`ps -o pid,ppid,stat,comm -p <PPID>`，问题在父进程不调 `wait()`
- **`D`（不可中断睡眠）**：进程卡在内核态 I/O 里，信号会排队，等它从内核态出来才生效。`kill -9` 之后它仍是 `D`，要解决的是磁盘或存储设备
:::

### 停止后确认它真的没了

```bash
ss -tlnp | grep 1234
```

**你应该看不到输出。** 端口还在监听说明还有别的进程（或另一个命名空间里的进程）占着，单纯看 `ps` 里的 PID 会被同一个程序的多进程结构骗到。

## 4. 「进程还在，但磁盘已经满了」

这是 `df` 和 `du` 对不上的经典原因：**文件被 `rm` 了，但进程的 fd 还指着它，内核不会释放块。** `du` 遍历目录看不到它，`df` 统计的是内核里的实际占用。

| 步骤 | 命令 | 你在找什么 |
| --- | --- | --- |
| 1 | `df -h /` | 确认到底是哪个文件系统满了 |
| 2 | `df -i /` | 排除 inode 用光 |
| 3 | `du -x --max-depth=1 / 2>/dev/null \| sort -h \| tail` | 真实的大头在哪 |
| 4 | `lsof +L1 2>/dev/null \| head -20` | **已删除但仍被打开的文件**（`+L1` = 打开且链接数为 0） |
| 5 | 找到 PID 后 `kill -TERM <PID>` 或重启它 | 释放块 |

**判断句：第 3 步和第 1 步差额巨大，且第 4 步有输出，就是这个原因。** 处理方式是重启那个进程，文件不用恢复。

`lsof` 不存在时的替代：

```bash
for p in /proc/[0-9]*; do
  ls -l "$p/fd" 2>/dev/null | grep -q '(deleted)' && echo "$p"
done
```

## 排障

**Q1：机器很卡，怎么判断是 CPU、内存还是 I/O 的问题？**

按这个顺序查，不要跳步：

1. `uptime` —— 看 load average 三个数。**load 高不等于 CPU 满**，D 状态进程也在 load 里
2. `top` 然后按 `1` —— 每个核一行。**所有核都接近 100% 才是 CPU 瓶颈**；只有一核满，多半是单线程程序
3. `free -h` —— `available` 那一列。接近 0 就是内存
4. `vmstat 1 5` —— `wa`（iowait）持续大于 0 就是 I/O 在拖后腿，`si`/`so` 非零说明在换页
5. `ps aux --sort=-%mem | head` 与 `ps -eo stat,pid,comm | grep '^D'` —— 定位到具体进程

**Q2：`kill` 说 `No such process`，但程序还在？**

1. `pgrep -af '关键词'` —— 拿到真实 PID，可能是你刚才记的 PID 已经变了
2. 你在容器里 —— `ps` 显示的可能是另一个命名空间。`cat /proc/1/comm` 看 PID 1 是谁
3. 程序是多进程的：主进程退了，worker 还在。`ss -tlnp` 看端口归属

**Q3：free 显示内存还有 40%，却 OOM 了？**

1. `dmesg -T | tail -50` —— 找 `Out of memory: Killed process` 那几行，**内核会写明杀了谁、为什么**
2. `cat /sys/fs/cgroup/memory.max` 和 `cat /sys/fs/cgroup/memory.current` —— 你在容器里，限制是 cgroup 级的，宿主机还有内存没用上
3. OOM 判定看的是**进程申请的那一刻**，不是你查询的那一刻。瞬时申请也会触发

**Q4：磁盘 100% 但 `du` 找不出大文件？**

1. `df -h` 确认是哪个分区
2. `lsof +L1` —— 被删除但仍被打开的文件
3. `journalctl --disk-usage` —— systemd 的日志可能占了几十 GB
4. `find /var/log -type f -size +500M -ls` —— 确认日志文件实体大小

## 什么时候别用

- **不要用 `kill -9` 当默认手段。** 它只是最后一步。正常运维流程是 TERM → 等 → 确认 → 才 KILL，直接上 `-9` 会把「程序为什么不响应 TERM」这个真正的线索永久抹掉。
- **不要在生产机器上用 `top` 排查完就关掉。** `top` 本身开销很低，但它的高刷新率输出在某些串口/采集通道上会影响别的程序。要留证据用 `ps` 快照或 `sar`。
- **不要靠 `free` 的 `free` 列做容量决策。** 用 `available`。同理不要因为 `buff/cache` 大就断定内存有问题。
- **`pkill -f '关键词'` 在生产上要格外小心。** 关键词宽一点（比如 `pkill -f python`）会把一堆无关服务一起停掉。**永远先 `pgrep -af` 把要杀的列出来，逐个确认 PID。**
- **`du /` 在大机器上很慢**，因为它要遍历每一个文件。养成 `du -x --max-depth=1 <可疑目录>` 的习惯，从上往下收窄。
- **容器里查 `ps`/`free` 看到的可能只是 PID 命名空间内的一部分。** 结论要结合宿主机的监控，不要拿容器内的数字直接告警。

## 哪些是通用的

| 这一章的判断 | Windows 上对应什么 |
| --- | --- |
| 「先按名字找 PID，再看细节」 | 任务管理器 / `Get-Process` / `tasklist` |
| 「默认温和停止，强制停止是最后一步」 | `Stop-Process` vs `taskkill /F`；服务对应优雅停止和强杀 |
| 「分清内存、磁盘、CPU 三种瓶颈」 | 任务管理器的性能页、事件查看器里的资源耗尽事件 |
| 「服务化进程用服务管理器管」 | sc.exe / `Get-Service`，Linux 上就是 [systemd](/linux/internals/11-systemd) |

**不通用的是信号模型。** `SIGTERM` / `SIGKILL` / 作业控制这套是 POSIX 的，Windows 上没有对应物（`.NET` 的 `CancellationToken` 是最接近的抽象）。跨平台写工具时，**能在语言层处理的中断就别用信号**。
