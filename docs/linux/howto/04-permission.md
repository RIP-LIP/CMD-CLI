# 权限：读懂 ls -l 的第一列，以及 rwx 不够用的时候

> 读完你能把 `ls -l` 第一列的十个字符无歧义地念出来，并知道什么时候该 `chmod`、什么时候该 `chown`、什么时候两个都救不了你。约 25 分钟。

<ModuleMeta module-id="04-permission" />

## 前置条件

确认你能在测试目录里反复改权限（**不要拿家目录试**）：

```bash
mkdir -p /tmp/perm-lab && cd /tmp/perm-lab
echo hello > a.txt
```

你应该看到：没有输出就说明成功。

确认你自己的身份和所属组 —— 后面所有「能不能访问」的判断都基于它：

```bash
id
```

你应该看到类似 `uid=1000(max) gid=1000(max) groups=1000(max),27(sudo)` 的输出。**先记住这两组数字和组名**，`sudo chown` 出问题时要用它们。

## 1. 把第一列拆成三段读

```bash
ls -l a.txt
```

你应该看到：

```bash
-rw-r--r-- 1 max max 6 Oct  4 16:20 a.txt
```

**判断顺序固定为：类型位 → 属主三位 → 所属组三位 → 其他人三位 → 结尾符号。**

| 位置 | 你要读出什么 | 这一章的例子 |
| --- | --- | --- |
| 第 1 个字符 | 是不是目录（`d`）、普通文件（`-`） | `-` 普通文件 |
| 第 2-4 个字符 | 属主（owner）自己的权限 | `rw-` |
| 第 5-7 个字符 | 所属组的权限 | `r--` |
| 第 8-10 个字符 | 既不是属主、也不在属主组里的所有人的权限 | `r--` |
| 第 11 个字符（有的话） | `+` 表示存在 ACL，`.` 表示带 SELinux 标签 | 见第 5 节 |

**同一个人可能同时命中「属主」和「所属组」两行，此时只按属主那一行生效**，组权限会被完全跳过。这是权限位最容易被误读的一处。

::: tip

结尾的 `.` 不是文件名的分隔符
`ls -l` 里权限位后面可能跟一个 `.`，它表示该文件带有 SELinux 安全上下文（`ls -Z` 能看到具体值）。`ls -lZ` 里 SELinux 标签失效时显示 `?`。**如果 `chmod 777` 之后你还是访问不了，先看这个。**
:::

## 2. 用八进制数字改权限

| 符号 | 数字 | 含义 |
| --- | --- | --- |
| `r` | 4 | 读 |
| `w` | 2 | 写 |
| `x` | 1 | 执行 |

每组三位是独立相加的。三个数合起来就是三位八进制数：

| 八进制 | 符号写法 | 用途 |
| --- | --- | --- |
| `644` | `rw-r--r--` | 普通文件默认：属主读写，其他人只读 |
| `600` | `rw-------` | 只给自己看的文件（SSH 私钥就该是 600） |
| `755` | `rwxr-xr-x` | 目录默认：属主进出自由，其他人可列出可穿过 |
| `700` | `rwx------` | 只给自己用的目录 |
| `664` | `rw-rw-r--` | 团队共享文件，需要同组可写 |
| `777` | `rwxrwxrwx` | **几乎永远是错的** |

| 命令 | 是否改动数据 | 说明 |
| --- | --- | --- |
| `chmod 644 a.txt` | ✅ 改权限 | 绝对覆盖成 644 |
| `chmod u+x a.txt` | ✅ 改权限 | 只在属主那一位加 x，其余不动 |
| `chmod -R 755 dir/` | ⚠️ 改权限，递归 | 目录里所有子目录和文件一起改 |
| `chmod --reference=b.txt a.txt` | ✅ 改权限 | 抄另一个文件的权限位 |

::: warning

`chmod` 是「绝对设置」，不是「加权限」
`chmod 644 a.txt` 会把三个位置**全部重写**。你以为在「加读权限」，实际把属主的执行位也抹掉了。所以**脚本里如果只想增不减，用符号写法 `chmod u+x`，不要用数字。**
:::

::: tip

`chmod +x`（不写属主）会跳过 umask 里关掉的位
`chmod +x` 的隐含含义是「对 a（所有人）加 x，但**umask 中被关掉的位不加**」。所以在你 `umask 077` 的机器上 `chmod +x script.sh` 只会得到 `-rwx------`，而不是所有人都能执行。**想让执行位明确落到每一位，用 `chmod 755 script.sh` 或 `chmod a+x script.sh`。**
:::

## 3. 目录上的 rwx 含义完全不同

**这是权限里最反直觉的一段：对文件，rwx 是三种独立能力；对目录，它们是三层门禁，缺一层就整条路断掉。**

| 目录权限 | 你能做什么 | 少了它会怎样 |
| --- | --- | --- |
| `r` | 列出里面的文件名 | `ls` 报 `Permission denied` |
| `w` | 在里面新建、删除、重命名 | `touch` / `rm` / `mv` 报 `Permission denied` |
| `x` | 进入它、访问里面的文件 | `cd` 报 `Permission denied`；即使能 `cd`，`cat` 里面任何文件仍会失败 |

**判断句：能删掉一个文件，靠的是目录的 `w` 和 `x`，跟这个文件自己的权限位一点关系都没有。**

```bash
chmod 755 /tmp/perm-lab
chmod 600 a.txt
rm /tmp/perm-lab/a.txt
```

第三条命令你会看到 `rm: cannot remove '/tmp/perm-lab/a.txt': Permission denied` —— 尽管你已经确认文件是 `600`、你就是属主。**因为删它是「改目录的内容」，看的是目录的 `w` 权限。** 这就是为什么「加个只读属性就删不掉」是误解。

## 4. 改属主：什么时候 chmod 根本救不了

| 命令 | 是否改动数据 | 作用 |
| --- | --- | --- |
| `chown max a.txt` | ✅ 改属主 | 只改属主，**所属组保持不动** |
| `chown max:dev a.txt` | ✅ 改属主和组 | 两者都改 |
| `chown :dev a.txt` | ✅ 只改组 | 冒号开头表示「属主不动」 |
| `chown -R max dir/` | ⚠️ 递归改属主 | 目录内全部 |
| `chgrp dev a.txt` | ✅ 只改所属组 | 等价于 `chown :dev` |

**判断句：改不了「谁能访问」，第一步先确认属主是不是别人。**

::: danger

`sudo chown -R` 是最容易造成大面积事故的命令之一
在有虚拟环境、node_modules、大量挂载点的目录上跑 `sudo chown -R`，会把容器里、挂载进来的卷、别的用户的文件一起改成你的属主，之后所有服务都以「权限不符」失败，而且没有一键还原的记录。

**动手前先看清楚会命中多少个文件：**

```bash
sudo chown -R --dry-run max /some/dir | wc -l
```

`--dry-run` 只打印不改，先数一遍行数。数量超出预期就别做了。
:::

::: warning

别人 `sudo chmod 777` 之后，问题往往没被解决
典型场景：文件属主是 `root`，你用普通用户 `chmod` 报 `Operation not permitted`；于是有人建议 `sudo chmod 777`。改完属主依然是 `root`，别的系统照样改不动它。

**判断句：`Permission denied` 出现在 chmod/chown 上，先问「这个文件的属主是我吗」，而不是先加 sudo 或加权限位。** 查法：

```bash
stat -c '%U %G %a %n' /some/file
```

你应该看到属主名和属组名。把属主改回你自己，再按需要给最小权限。
:::

## 5. 文件是怎么被创建出来的：umask

新建文件**不会**拿到 `777`。它拿到的是「目标权限再被 umask 削掉」，所以默认值是 umask 决定的：

| 创建动作 | 计算方式 | umask 022 的结果 | umask 077 的结果 |
| --- | --- | --- | --- |
| 新建普通文件 | `666 & ~umask` | `644` | `600` |
| 新建目录 | `777 & ~umask` | `755` | `700` |

```bash
umask
```

你应该看到 `0022`（部分系统是 `0002`，表示同组可写 —— 这正是很多团队共享目录的默认来源）。**看到 `002` 结尾和看到 `022` 结尾，行为不同，值得多看一眼。**

改当前 shell 的 umask：

```bash
umask 0027
```

**判断句：umask 只影响之后新建的东西，已经存在的文件一个字都不改。** 要改已有文件的权限，只能回到第 2 节的 `chmod`。

## 排障

**Q1：`Permission denied`，但我明明是属主？**

按这个顺序查，不要跳步：

1. `ls -l 文件` —— 看第 1 个字符：如果是 `d` 而你以为它是文件，说明你操作的对象搞错了
2. `ls -ld 所在目录` —— 目录上少了 `x`，你连进去的资格都没有。注意**必须带 `-d`**，不加会列出目录内容
3. `stat -c '%U %a' 文件` —— 属主是不是你、权限位和你以为的是否一致
4. 走到这里还是不通，看第 5 节的结尾符号：`+` 走 `/linux/internals/15-acl`，`.` 查 SELinux（`ls -lZ`）

**Q2：`chmod u+x script.sh` 之后直接运行，还是 `Permission denied`？**

1. `ls -l script.sh` —— 确认 x 位真的加上了
2. `head -1 script.sh` —— 看有没有 BOM 或 `#!/bin/env python3` 之类写错的解释器路径
3. `file script.sh` —— 确认它不是 CRLF 换行（Windows 编辑过的脚本在 Linux 上会报 `bad interpreter: /usr/bin/env bash^M`）
4. 如果是脚本调了别的命令却报「找不到」，那是 `PATH` 问题，不是权限问题 → [环境变量与计划任务](/linux/internals/14-cron)

**Q3：`cp` 过来的脚本为什么就没法执行了？**

1. `ls -l 原文件 目标文件` —— 对比两边的 x 位
2. 结论：新建文件的权限是源文件权限再被 umask 削掉，x 位就是这样没的
3. `chmod 755 目标文件` 修回；要连带时间戳一起保留用 `cp -p`

**Q4：`sudo chmod 777 /some/dir` 之后，里面还是访问不了？**

1. `ls -ld /some/dir` —— 777 的是目录自己，**里面的每一层也要能穿过**
2. `namei -l /some/dir/目标文件` —— 一层一层把路径上的权限列出来，是这类问题最快的定位手段
3. 逐层补 `x`，别用 `-R 777`

## 什么时候别用

**能不改权限就别改。** 这一章的技巧在下面几种情况下不该用：

- **别用 `chmod 777` 解决「跑不起来」**。跑不起来的原因通常是缺执行位（`+x` 就够）、解释器路径错、或者 CRLF 换行。`777` 只会掩盖真实错误，并让文件对所有人可写。
- **别用 `sudo` 掩盖「属主不对」**。属主不对就 `chown` 回去，或者让正确的人执行它。用 sudo 执行自己的脚本会生成 root 属主的产物文件，久了目录里全是混合属主的垃圾。
- **一个人的场景不要碰 ACL**。`setfacl` 适合多人共享，`+` 结尾会让人误以为权限有异常，排查成本高于收益。人数只有一两个时，新建一个共享组 + `chgrp` 更干净 → [ACL 精细授权](/linux/internals/15-acl)。
- **`chmod -R` 不要在 `/`、家目录根、挂载点下面跑**。递归没有确认、没有回收站，跨文件系统的边界还会静默跳过一部分。
- **只在自己的机器上、只在自己建的测试目录里练本章的命令**。生产机器上的权限改动应当走变更流程。

## 哪些是通用的

| 这一章的判断 | 换到哪里还成立 |
| --- | --- |
| 「先看属主，再看权限位」 | Windows 的 NTFS 权限面板、macOS 的 `ls -l@` 共享目录 |
| 「能删文件看的是目录的权限」 | Windows 上删除受目录 ACL 里的 `Delete` / `Delete subfolders and files` 约束，同一条规律 |
| 「默认权限由 umask 决定」 | Windows 上由「文件夹属性 → 安全 → 高级 → 继承」决定默认 ACL，是同一件事的另一副面孔 |
| 「递归改属主前先 `--dry-run` 数一遍」 | 任何批量提权操作前先看影响面 |

**不通用的是八进制数字本身。** `644` 在 Linux 上是约定俗成，在 Windows 上没有对应物，在 FreeBSD 上 `wheel` 组的约定也不同。**先看目标机器 `umask` 输出是什么，再决定数字。**
